ABSTRACT
Garbage Collection (GC) is a representative automatic memory
manager widely deployed in popular programming languages, such
as Java, C#, and Golang (Go). Through GC, these languages provide
programmers with flexibility and safety. However, GC leads to
non-trivial overhead in compute and memory resources during
application runtime. GC threads compete with non-GC threads
(mutators) of an application, which particularly impacts latency-
critical (LC) applications and causes long tail latency. Existing GC
approaches do not efficiently address the interference, as GC is
triggered passively without a global insight of the application; or
they employ incremental GC to reduce the interference, while the
incremental progress is not dynamically tailored during GC process
according to runtime characteristics, which leads to significant
performance degradation upon bursty requests.
We present LEGO, an efficient and non-intrusive GC framework
that deploys a novel elastic incremental GC mechanism integrated
with an adaptive GC scheduler to reduce CPU contention between
GC and mutators, and improve resource utilization and QoS of LC
applications.WechoosetodevelopLEGOinGo,asGoisspecifically
designed for cloud applications and the current GC mechanisms for
JVM are ineffective for Go due to its unique GPM thread scheduling
and memory allocation model. LEGO adapts incremental GC into
Go to tackle the full GC issue and addresses resource contention
with a proactive scheduler for adaptive GC triggering. Importantly,
LEGO leverages the elastic incremental GC mechanism in miti-
gating the interference from unavoidable GC in face of bursts of
requests. We implement and evaluate LEGO with popular LC appli-
cations developed in Go. Results show that compared to the default
Go GC and a tailored G1 GC, LEGO significantly improves both the
tail latency and throughput for LC applications.

1 INTRODUCTION
Cloud computing has achieved remarkable success over the last
decade due to features including resource sharing, felxibility, and
scalability. Cloud systems also require fast and safe concurrency
provided by programming languages. This is where Golang (a.k.a
Go) comes for, which is also known as Language of Cloud. Designed
for high concurrency, Go emphasizes concurrent programming
for cloud systems. It is being used to build popular cloud applica-
tions [5–7, 41] at a massive scale.
Asmanymodernprogramminglanguages,Goisanauto-memory
management language. Instead of explicitly removing obsolete ob-
jects, it deploys GC for memory management. GC is executed auto-
matically in background to reclaim memory for the runtime heap.
During GC runtime, it may pause the entire application, a phenom-
enon known as Stop The World (STW) [18] in other languages such
as Java.
Motivation. Go’s unique GPM model is designed to improve
thread-switching performance. Different from the state-of-the-art
GCs, such as G1 GC [24], ZGC [20] and Shenandoah GC [19] for
the Java Virtual Machine (JVM), Go employs a concurrent, non-
generational, and non-incremental GC. This corresponds to less
STW overhead, a runtime heap layout without distinction between
young and old objects, and the ability to run GC on the partial mem-
ory heap. Go also leverages the TCmalloc memory allocator [26],
which allocates objects at the thread level, whereas JVM allocates
objects from a universal heap when the thread-level stack buffer is
full. Furthermore, Go GC is non-copy-and-compact. These features
169HPDC ’23, June 16–23, 2023, Orlando, FL, USA Junxian Zhao, Xiaobo Zhou, Sang-Yoon Chang, & Chengzhong Xu
make existing GC optimizations for JVM not suitable or inefficient
for Go.
We find Go applications often experience significant latency,
particularly tail latency in face of CPU interference and bursty
requests. GC threads interfere with non-GC threads (mutators),
which results in performance degradation of latency-critical (LC)
applications. Our experiments show that GC interference on LC
applications such as key-value stores developed in Go can cause up
to 4× increase of the 99th percentile (p99) query latency compared
to when the key-value stores are running without GC. The tail
latency becomes more severe when the input requests are bursty.
Even worse, our experiments find that GC is more likely (more than
2×) to be triggered in face of bursty requests.
Therefore,GodemandsforanewGCmechanismandascheduler
that take into account interference of resource usage introduced by
mutators of the concurrent GC. Specifically, Go GC should satisfy
the following requirements for maintaining service level objective
(SLO) of LC applications.
• LC applications should maintain low tail latency for meeting
its SLO objectives.
• The new GC should reduce its interference on mutators of
the application, especially upon bursty requests.
• ThenewGCneedstobetransparentandgenerallyapplicable
to all applications developed in Go. Thus, the source code of
applications need not be modified.
Limitation of state-of-the-art approaches. There are work
in memory management focusing on GC optimization, mostly in
JVM.Previousworks[32,37,38,51]introducednewalgorithmsand
modified heap layout to reduce GC overhead. Recent works [28, 50]
propose to schedule with fine-grained hardware resources, i.e. CPU
and memory, for different threads in GC. There are also studies [44,
45] that focus on GC on far-memory and resource disaggregated
systems. However, due to the semantic gap between JVM and Go
designs, most of the existing optimizations are not available or
directly applicable for Go. Importantly, the existing works lack
runtime adaptivity for incremental GC design.
Challenge I - pre-fixed incremental volume. The production G1
GC deploys an incremental GC mechanism for JVM, where the GC
pause time and reclaimed memory volume are pre-fixed when an
application is started up or during a non-GC period. However, G1
GC cannot elastically decide the volume of the current GC during
GC runtime. In face of bursty requests, GC activities dramatically
increase the latency of an application violating its SLO. This is un-
avoidable in the design of the current incremental GC mechanism.
Challenge II - passive GC triggering. The state-of-the-art GCs
(suchasG1GC,ZGCandShenandoahGC)onlytriggerGCprogress
early enough to avoid Out Of Memory (OOM) errors. They do not
consider the resource usage of GC progress at runtime. The default
GC in Go limits the total CPU time usage of GC progress to a
30% threshold, which does not delicately match the runtime CPU
usage. GC progress tends to compete CPU resources with mutators
dynamically. However, the Go scheduler triggers GC even when the
CPUusageishigherthan70%,whichcanleadtosevereperformance
degradation in latency-critical applications.
Challenge III - integration into Go. The existing GC optimizations
are difficult to be directly transplanted into Go, as Go employs a
different memory layout, i.e., GPM model, and it uses TCmalloc
and non-copy-and-compact GC. Currently, the default Go GC only
supports full GC.
Key insights and contributions. In this paper, we present
an efficient, non-intrusive GC scheduling framework, LEGO that
deploys a novel elastic incremental GC mechanism integrated with
an adaptive GC scheduler to reduce CPU contention between GC
and mutators, and improve resource utilization and QoS of LC
applications developed in Go.
To address the first two challenges (pre-fixed incremental vol-
ume and passive GC triggering), LEGO designs a unique adaptive
incremental GC mechanism that proactively triggers GC and dy-
namically tailors the incremental progress during GC according
to runtime characteristics. Specifically, it obtains GC processing
volume at runtime in face of detecting a burst of requests, and
proactively triggers and adjusts the GC processing volume based
on the available resources. To facilitate its adaptive incremental
GC, LEGO designs Quad-Color marking algorithm for dynamically
GC triggering.
To address the third challenge, LEGO adds new data structures
(write barrier and P&G-level remember set) for recording object
reference modifications and Goroutine migration during GC run-
time. Furthermore, it adds a P-level reference counter to reduce the
overhead of Goroutine migration and maintain the consistency of
object reference during GC.
This paper makes the following contributions.
• We conduct in-depth characterization and analysis of Go GC
interference on LC applications, especially its performance
impact upon bursty requests. We apply a statistic approach
that leverages on the obtained runtime characteristics for
diagnosing GC interference.
• We design an elastic incremental GC mechanism with a
proactive GC scheduler. Furthermore, we develop a Quad-
Color marking algorithm for dynamically triggering the in-
cremental GC mechanism.
• We implement LEGO in Go runtime. It is transparent to
applications and the OS. LEGO enables flexible and robust
GC, which can be deployed in any mark-and-sweep GC
system including JVM GC.
We evaluate LEGO with popular Go-developed cloud applica-
tions (Badger, Bolt, Rosedb, and TiDB) and benchmark workloads.
Experiment results show that LEGO can reduce the average 99th
percentile latency up to 35.6% and 42.7%, and improve the system
throughput by 33% and 42% compared to the default Go GC and a
tailored G1 GC, respectively. LEGO software artifact is available at
https://github.com/lotusknight/LEGO.
Limitations of the proposed approach. LEGO considers LC
applications that have bursty requests. It reschedules GC with tran-
siently available system resources. It is possible though uncommon
that an LC application receives consistent high volume of traffic. In
this scenario, GC may be triggered frequently or even continuously.
LEGO would be less or ineffective compared with the default Go
GC. Note LEGO can be transiently switched to the default Go GC.
Currently, LEGO supports Go programs. Its principle and design
can be applied to any programming language runtimes including
JVM that employ automatic memory management.

2.1 Go Thread Scheduling and Heap Layout
Thread scheduling. Go introduces a unique GPM model as ab-
stracts for flexible and low-overhead runtime thread management
and concurrent programming. Figure 1 shows the abstract model.
G (Goroutine) is the basic execution unit in Go, which is detached
from an OS-level thread to reduce thread switching overhead. Dif-
ferent Gs run in parallel during runtime. Similar to a process in
Linux, each G has execution states such as 𝑟𝑢𝑛𝑛𝑎𝑏𝑙𝑒 and 𝑟𝑢𝑛𝑛𝑖𝑛𝑔.
The solid gray G represents the current running Goroutine, while
a white blank G is not being executed by any thread. Multiple Ms
represent OS-level threads. Each P (processor) must be attached
to a M (machine). Go runtime can reschedule a P to a different M.
Each P has a local queue for 𝑟𝑢𝑛𝑛𝑎𝑏𝑙𝑒 Gs. By running on an M,
P executes Gs from its 𝑟𝑢𝑛𝑛𝑎𝑏𝑙𝑒 queue. Compared with runtime
thread switching based on system calls, G switching is more flexible
as P reuses the same OS thread (M) for running different Gs. With
the GPM model, Go reduces overhead in creating and scheduling
threads.

2.2 Garbage Collection (GC)
Go GC semantics. Fig 3 shows four phases in Go GC, 1) Sweep
termination (STW), 2) Mark phase (GCmark), 3) Mark termination
(STW, GCmarktermination), and 4) Sweep phase (GCoff). In each
GC cycle (phases 1 to 3), Go scans the whole heap and marks
alive objects. Two phases (STWs and Concurrent Marking) are
executed during this period. Concurrent Marking time is much
longer (>100X) than STW time. During the Concurrent Marking
phase, mutators are running in parallel with GC processes. Each
allocation by a mutator is followed by a number of scan operations,
𝐴𝑙𝑙𝑜𝑐𝑎𝑡𝑒𝐴𝑠𝑠𝑖𝑠𝑡.AfteracompleteGCcycle,inphase4Gosweepsand
reallocates obsolete objects when a new object is allocated, which
is also concurrent. Note Go does not deploy a generational GC
mechanism, instead, the objects in runtime heap are non-movable.
They are allocated in their final positions, which is different from
the traditional GCs in JVM. Thus, JVM GCs cannot be directly
transplanted to Go since they have different basic GC logics, i.e.
JVM adopts copy-and-compact GC.
Tri-color marking. All tracing-based GCs use tri-color marking
algorithm [10]. It traces reachable objects from RootSets. When the
marking phase starts, it puts all objects in RootSets to a list which
grays them. GC worker threads fetch objects from the list and trace
pointersfromtheobjects.Objectswithuntracedpointersaregrayed
and put into the list recursively. Other reachable objects are marked
black. Three colors, white, gray and black, represent different states
of marking: 1) a white object is not currently reachable, 2), a black
object is reachable and all its pointers are traced, 3) a gray object is
marked, while it has pointers not exhausted by scan worker threads.
Gray objects are put in a work list for further tracing. When the list
of gray objects is empty, the Concurrent Marking phase is finished.
The white objects left are unreachable and can be swept in the later
phase.

We examine the interesting phenomenon and reveal that the
current Go GC use a heap usage increment ratio mechanism to
predict how early enough does it trigger GC to avoid OOM errors.
Thus, a burst of requests represents a higher rate of heap usage
increment ratio, which in return results in a higher probability
of reaching the GC threshold since a large number of objects are
allocated in the heap. As a result, more requests are involved when
GC is running during a burst of requests, which leads to more
significant tail latency.
The state-of-the-art GCs, including both Go GC and JVM GCs,
are triggered passively, whether in a fixed time interval or in a pre-
dictive way to avoid OOM errors. Such a GC triggering mechanism
is unable to address the high tail latency when a burst of requests
arrives. To tackle the identified issues, we propose and develop
LEGO, a proactive GC, currently implemented for Go GC, with
different GC triggering policies. To mitigate the interference from
GC, we design and develop an elastic incremental GC mechanism
that minimizes the GC overhead on mutators.
3 LEGO DESIGN
LEGOconsistsoftwoimportantcomponents,anelasticincremental
GC mechanism and an augmented Go GC scheduler. Figure 7 shows
itsdesignstructure.TheelasticincrementalGCmechanismconsists
of an incremental GC mechanism and an elastic GC controller. The
GC scheduler determines the timing and volume of GC, both before
and during a GC period. It also decides which policy is used for GC
triggering. The elastic incremental GC mechanism receives signals
from the GC scheduler and executes the adaptive GC process.
3.1 Incremental Go GC
The current Go GC supports full GC only, which is triggered on the
whole runtime heap and is unable to be paused or stopped during
a GC period. LEGO features incremental Go GC, tailoring for its
uniqueGPMmodelandmemoryallocator.ToadaptincrementalGC
into Go, LEGO splits GC and non-GC objects. Go uses TCmalloc
for memory allocation and allocates objects at the thread level.
LEGO makes use of it to depart GC into the P level to minimize the
modificationinGoruntime.WithoutreschedulingofGoroutines,all
Goruoutines in one P share the same P-level cache,𝑚𝑠𝑝𝑎𝑛. LEGO
triggers GC on P-level to minimize the number of cross-region
references. However, Go scheduler reschedules Gs into idle Ps for
load balancing, which asks for a specific solution to maintaining the
validity of reference tracing during GC. Section 4 further illustrates
how LEGO tackles the Goroutine immigration issue.
3.2 Elastic GC Controller
LEGOintroducestheelasticGCcontrollerfortwogoals,1)usingthe
incremental GC mechanism that executes controllable GCs within
a shorter time period and involves less resource interference, 2)
dynamically determining the volume of GC to be triggered in each
GC cycle. The second goal is crucial in tackling bursty requests. The
elastic incremental GC grants LEGO the capability to adaptively
execute GC based on the system runtime characteristics. It can
shorten and stop an ongoing GC when a burst of requests arrives,
and execute a full GC when CPU resource usage is not intense.
However, the state-of-the-art GC marking algorithm, tri-color,
is unable to dynamically determine the volume of incremental
GC during a GC period. The tri-color marking algorithm can only
distinguish 𝑚𝑎𝑟𝑘𝑒𝑑, 𝑢𝑛𝑚𝑎𝑟𝑘𝑒𝑑, and 𝑜𝑛𝑔𝑜𝑖𝑛𝑔 objects during a GC
period. The two states,𝑠𝑐𝑎𝑛𝑛𝑎𝑏𝑙𝑒 (all objects involved in the chosen
heap area during a GC period) and 𝑢𝑛𝑠𝑐𝑎𝑛𝑛𝑎𝑏𝑙𝑒 (vice versa), are
pre-fixed in all state-of-the-art GCs. It is impossible to switch the
state of 𝑢𝑛𝑠𝑐𝑎𝑛𝑛𝑎𝑏𝑙𝑒 objects to the state of 𝑠𝑐𝑎𝑛𝑛𝑎𝑏𝑙𝑒 objects. To
adaptively decide the volume of GC during a GC period, LEGO
extends the tri-color marking algorithm with the fourth color.
3.3 Quad-Color Algorithm
To support the elastic incremental GC mechanism, we introduce
a new Quad-Color algorithm during GC mark phase. It is used
for the elastic GC controller. Figure 8 shows the Quad-Color state
transform workflow.
We introduce several terminologies. ∼𝑇 is the collection of Ps
not included in the current 𝑠𝑐𝑎𝑛𝑛𝑒𝑑 or 𝑠𝑐𝑎𝑛𝑛𝑖𝑛𝑔 Ps, while𝑇 is the
collection of Ps included in the current 𝑠𝑐𝑎𝑛𝑛𝑒𝑑 or 𝑠𝑐𝑎𝑛𝑛𝑖𝑛𝑔 Ps. Set

3.4 GC scheduler
The GC scheduler fetches runtime characteristics from the monitor,
including the CPU usage, heap usage, and heap increment ratio of
the application. Based on the runtime characteristics, the scheduler
determinesthetimingandthevolumeofGCtriggering.Weconsider
three scheduling policies.
• A - Earliest First. The GC scheduler triggers GC as early
as possible when CPU usage is below a threshold. Policy
A increases the probability of triggering GC at low CPU
usages, which can be favorable for a LC application with
bursty requests. However, the policy may also lead to a high
GC frequency when the application is under low workload.
To reduce the frequency of unnecessary GCs, a minimum
heap size threshold is introduced for GC triggering.
• B - Default Augmented. The GC scheduler triggers GC when
the heap size reaches a similar threshold as in the default Go
GC. It makes sure that the threshold can avoid OOM errors.
This policy compromises the CPU usage on GC and the tail
latency of the application.
• C - Predictive. GC scheduler uses ARIMA [34] model to pre-
dict the input pattern and trigger GC under low request
pressure. With correct predictions, this policy can offer the
best performance among all three policies. However, the pol-
icy also requires training datasets in prior for each running
application.
GC volume determination. The coordination of GC volume
with the quad-color algorithm is achieved by monitoring runtime
CPU usage during GC and limiting the number of Ps accordingly.
This ensures that the CPU is not fully occupied by GC threads with
the assigned Ps. Furthermore, the GC scheduler monitors runtime
CPU usage to determine whether to add more Ps into T during the
current GC period. In the first two policies, the scheduler naively
references runtime CPU usage to make decisions. The threshold
varies depending on different applications and system setups, so
we add a parameter for user customization. In the experimental

setup, we empirically set the CPU usage threshold at 40%, as this is
the average CPU usage when the testbed server reaches its max-

In Predictive policy, LEGO leverages prediction to select the
most suitable time for GC triggering. The GC scheduler directs
LEGO to determine how many Ps to execute while maintaining low
CPU interference. With the reliable workload prediction of ARIMA,
LEGO is more likely to trigger full GC instead of incremental GC.
Using full GC for memory reclaim is more effective when the CPU
resourceisabundant,whileusingincrementalGCiscomplementary
to the full GC under high CPU utilizations.
GC triggering timing. The default full GC executes faster than
the incremental GC, as it needs less metadata and scans all Ps at the
same time. Thus, the threshold of GC triggering in the default Go
GC is the baseline, i.e., latest GC triggering. Under this condition,
LEGO switches back to full GC to avoid OOM errors. In LEGO,
the concurrent marking time is prolonged while the CPU usage is
decreased.WhenLEGOfacesburstyrequestsandGCisunavoidable,
it triggers GC at the lowest level, i.e., one P at a time. Under this
condition, we need to ensure the memory is not over the limit.
The time to the full GC threshold depends on the number of Ps in
the application. LEGO calculates the average time consumption on
each P’s marking, and multiplies it with the number of Ps to get
the latest time interval ahead of the default full GC for triggering
the elastic incremental GC mechanism.
Ps enqueue rule. The GC scheduler is also responsible for the
ranking of Ps. Here, LEGO uses the least recently scanned list to
store all Ps. With the list, LEGO ensures that all Ps have equal
opportunity to be chosen during the execution.
4 IMPLEMENTATION
We implement LEGO upon Golang 1.16.6 on Ubuntu 21.04. Here, we
discuss the important data structures and illustrate how to address
the Goroutine immigration issue.
The elastic incremental GC mechanism asks for delicate infor-
mation of cross references during runtime. Cross references record
the references between different Gs or even between different Ps.
We change write barriers in Go to keep the records of these updates.
Three levels of metadata are introduced, G, P, and heap levels. G-
level remember sets record all references from the source G out of
the current G. P-level masks record how many Ps are referenced
by the current P. There are also objects that are moved from the G
stack and private cache to the universal heap. We add a function to
record the relationship between G and P.
Remember set. Each cross reference is at G level or the heap.
A remember set records the reference from its destination to the
source, which is necessary for incremental GC execution and Gor-
outine immigration. LEGO records the references by changing the
default write barrier and adding entries in the remember set. To
distinguish different types of objects in Figure 8, LEGO introduces
remember sets at both G level and the universal heap. For G level,
it records the cross references from objects in other Gs to the ob-
jects in the current G. The heap level remember set records all the
objects that escaped from Gs. With the remember set, LEGO can
categorize objects into different states during GC. Meanwhile, as
Go scheduler reschedules Gs for load balancing, the remember set
is also necessary to be used for maintaining the cross reference
tracing logics consistently.
Bit mask. Since LEGO triggers GC in the P-level manner, we
deploy a P-level mask to reduce the overhead of comparison when
new Ps are added during GC runtime. The mask is made of two
parts, a reference mask and a reference counting table. P-level bit
mask records the cross-reference from the other Ps. Each bit in
the mask represents the corresponding P, which owns at least one
Goroutine where its objects have references pointing to the current
P. The table records the number of Gs referenced by those Ps, which
are used to address Goroutine immigration issue. The Reference
mask is a bit mask that only paints the bit of reference source
granularity.
Goroutine immigration. For load balancing, the Goroutine
scheduler schedules𝑟𝑒𝑎𝑑𝑦 state Goroutines from busy Ps to idle Ps.
For example, a Goroutine G1 immigrates from P1 to P2. All existing
objects in the immigrated Goroutine are allocated in P1’s 𝑚𝑠𝑝𝑎𝑛
MS1, and new objects will still be allocated on MS1 if there are
empty slots. As a result, a 𝑚𝑠𝑝𝑎𝑛 from P1 is shared by G1, while
G1 belongs to P2. If P2 is included in T while P1 is not, we cannot
recycle the currently unreferenced objects on MS1, as they might
be referenced by objects in P1. Without an effective way, Goroutine
immigration would corrupt the incremental GC logic and lead to
memory-leak issues.
A direct record of all cross-references will be a catastrophe when
new Ps are added into T. Thus, LEGO employs P-level bit masks
with the reference counting table. By comparing the bit masks with
the current T, LEGO categorizes the objects into four states based
on the quad-color state transform workflow, as illustrated in Fig 8.
The reference counting table is used when a Goroutine is removed
from its current P. Then, all related reference counting numbers are
reduced by 1. If some value reaches zero, the corresponding mask
bit is cleaned. This is processed during Goroutine immigration,
which mitigates its impact on GC performance.

5.8 Overhead
LEGO introduces the elastic incremental GC mechanism that dy-
namically determines the GC volume at runtime. Compared with
the default Go GC, LEGO employs an always-on write barrier for
object recording, which increases the average request latency by
up to 2%. LEGO also increases the basic heap usage due to the extra
data structure for cross-references, which implicitly increases the
frequency of GC. However, the benefits of the elastic incremental
GCmechanismandadaptiveGCschedulersignificantlyoutperform
the overhead. Note that the number of Ps is counted by the default
Go runtime. LEGO does not introduce overhead in this regard.

6 RELATED WORK
LC Application QoS. Many studies focus on meeting the SLO of
LCapplicationsfromtheperspectiveofreducingthetaillatency[11,
23, 25, 39, 52]. For example, PerfIso [28] is on CPU isolation for
CPU sharing between LC applications and batch jobs. FlatStore [16]
is a KV store that uses logs in persistent memory for serving data
requests. Caladan [25] proposes a new CPU scheduler in the Linux
kernel that improves QoS of LC applications, especially the tail
latency. Perséphone [23] is a novel kernel-bypass OS scheduler
designed to minimize the tail latency for applications executing at
the microsecond scale. LEGO tackles the GC interference on LC
applications, which is orthogonal to those studies.
GC Optimization. Most studies on GC are focused on JVM [12, 24,
27, 27, 33, 36–38, 46, 49–51]. LXR GC [51] demonstrates the produc-
tionG1GCyieldssmallertaillatencyforLCapplications,compared
with the concurrent GC mechanisms such as ZGC GC [20] and
Shenandoah GC [19]. Though G1 GC incurs more STW pauses,
the overall tail latency is indeed reduced. Yak [37] develops a
GC algorithm for distributed data processing systems. ROLP [12]
profiles object lifetime and uses the profiled information for effi-
cient GC. iGC [50] introduces a proactive GC to reduce the tail
latency in cloud environments. Different from the most tracing
GCs, LRX GC [51] evolves the original reference counter based
GC and achieves significant improvement on LC application QoS.
However, the mechanism does not apply for Go, because Go GC is
neither generational nor copy-and-compact. Platinum [47] lever-
ages idle cores during STW pauses and grants them to mutators for
utilizing idle computing resources. LEGO focuses on Go GC, while
its adaptive incremental GC mechanism can also be extended and
deployed in other automatic memory management programming
languages.
GC in New Systems. There are GC studies focusing on new sys-
tems, such as non-volatile memory (NVM) and far memory systems.
For example, Semeru [44] provides a distributed GC that offloads
object tracing to memory servers so that tracing is performed close
to data in memory-disaggregated systems. Work [48] optimizes GC
atop NVM systems by introducing two NVM-aware optimizations,
write cache and header map, to tackle the bandwidth limitation
of NVM. Memliner [45] improves the performance of far-memory
systems by lining up memory accesses, which alleviates the gap
between the application QoS and the GC.
Performance Interference and Isolation. Prior works have in-
tensively tackled performance interference in several ways. Early
approaches disallow LC applications from sharing resources with
other applications to avoid performance interference [13–15, 31,
39, 40, 42, 43]. Other early approaches avoid co-scheduling applica-
tions that are likely to interfere with each other [21, 35]. The third
category of research focuses on eliminating interference altogether,
by partitioning and isolating resources among co-scheduled ser-
vices with feedback control based techniques [22, 29, 31, 39]. LEGO
tackles the interference between GC threads and mutators of LC
applications, which is complementary to the existing studies.
7 CONCLUSION
LEGO is motivated by severe performance degradation due to the
CPU interference between concurrent GC threads and mutators of
LC applications during GC runtime in face of bursty requests. We
find that proactively scheduling GC threads under low CPU usages
opens up a significant opportunity for application performance
improvement. LEGO designs the adaptive incremental GC mech-
anism for the first time. We develop LEGO in Go, as the current
GC mechanisms for JVM are ineffective for Go due to its unique
GPM thread scheduling and memory allocation model. Experimen-
tal results show that compared to the default Go GC and a tailored
G1 GC, LEGO significantly improves both the tail latency and the
throughput for LC applications developed in Go.
In future, we plan to extend LEGO to other programming lan-
guages that deploy automatic memory management.
